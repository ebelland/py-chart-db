N-20  Figure/Axis/Series properties: share a BaseProperties base class [DONE]
      Started by hand (a QWidget subclass whose __init__ called
      self.setLayout(QVBoxLayout())) and made all three widgets tiny
      (22x22): a QWidget accepts exactly one layout, so every subclass's
      own QVBoxLayout(self) in its _build_ui() silently lost to the one the
      base had already claimed, leaving each panel's real controls built
      but never attached to anything the widget would actually size itself
      by. Fixed and finished properly:
      - BaseProperties (app/widgets/base_properties.py) sets no layout -
        every subclass still owns its own _build_ui(). It does own the
        four attributes all three read/wrote identically (_repo,
        _figure_id, _figure, _redraw_callback) and set_connected_figure/
        clear_connected_figure, which were three near-identical copies.
        _before_reload() is the one extension point a subclass needs
        (FigurePropertiesWidget pushes this figure's own DPI/size into
        rcParams there, before the fields that read it reload).
      - Regression tests in test_base_properties.py pin the layout bug
        specifically (each editor's own layout must have content,
        sizeHint must not be QWidget's bare default) so this class of
        mistake cannot silently return.
      - Along the way: adjusting BaseProperties' QSS surfaced that
        fluent_win11.qss's card selector (#Card/#card, an object name)
        never matched create_card_widget()'s actual output (property
        card=true) - see N-17's note, same root cause, fixed there.
        BaseProperties itself got #basePropertiesPanel (transparent, so it
        never paints a surface between the cards that already do - matches
        how System Settings and the WinUI3 Settings app are themselves a
        transparent page with individually card-framed sections on it).
      - Also reconsidered N-17's "force Fusion" fix while here: forcing it
        app-wide (the first version) would have overridden every native
        Aqua/Fluent control macos_native.qss deliberately leaves unstyled,
        undoing its own stated design. Rescoped to
        apply_fusion_for_item_view_styling(view), applied only to
        TableListPanel's and TablePreviewPanel's own QTableView - the two
        views that actually style QAbstractItemView selection/headers
        directly - via QWidget.setStyle() rather than
        QApplication.setStyle(). Tests for both changes verify via a
        setStyle() spy, not by reading widget.style() back afterwards:
        once any app-wide stylesheet is active, Qt wraps a widget's true
        style in a private QStyleSheetStyle proxy whose
        metaObject().className() always reads "QStyleSheetStyle"
        regardless of what it wraps - reading it back would look identical
        whether the fix is in place or not.

N-19  GUI: toward a more standard, easy, intuitive interface
      Requested generically ("una GUI piu' standard, facile ed intuitiva");
      these are the concrete points actually observed hands-on this round,
      not a generic UX checklist - each names a specific place, not a
      principle.
      - Properties panels (Figure/Axis/Series) are Apply-then-look: nothing
        shows what a change will do before it is applied and the chart
        redraws. Even a lightweight inline preview (a small thumbnail, or
        highlighting which control touches which part of the chart) would
        close that loop faster than switching eyes between the form and
        the tab.
      - The Series properties selector is a plain-text combo; each entry's
        series already has an actual plotted colour. A small colour swatch
        per row (matching MatplotlibColorCombo's own approach elsewhere)
        would make "which series is this" recognisable without opening it.
      - The activity rail (Data / Chart options / Series operations) is
        icon-only with tooltip-only labels - fine once learned, but nothing
        in the running app teaches a first-time user what the four icons
        are for beyond hovering each one. Worth checking whether a
        one-time label (or a "?" walkthrough) is worth the added chrome,
        given nav rail structure itself is being kept as-is per the
        Finder-sidebar discussion.
      - Import dialog shows delimiter/encoding/skip-rows controls
        regardless of the chosen source - irrelevant for Excel or a
        database table, relevant only for delimited text. Progressive
        disclosure (hide what the current source cannot use) would read as
        less cluttered than always-visible-but-inert controls.
      - Manual spacing (Figure properties) asks for six raw 0..1 fractions
        with no visual feedback - a live-updating preview, or drag handles
        on the chart itself, is the more standard way this kind of control
        is usually presented, though it is a real redesign, not a quick
        pass.
