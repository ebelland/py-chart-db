N-20  other rendering backends and richer ChartPanel interactivity - a
      brainstorm, not yet scoped work
      Matplotlib stays the renderer of record: every chart type, every
      series operation and the whole descriptor model are built on it, and
      duplicating that surface for a second backend is not worth it. Two
      narrower integrations pull their weight instead:
      - pyqtgraph as a second, *optional* renderer for one axis at a time,
        picked when interaction matters more than chart variety: OpenGL
        line/scatter that stays smooth at counts where Matplotlib redraw is
        the bottleneck, a built-in crosshair, and mouse-driven ROI/region
        select for free (this is the natural engine behind P2-4, not a
        replacement for it). A closer fit than QtCharts here - QtCharts is
        fast but its chart-type and annotation vocabulary is much narrower
        than what this app's descriptors already express.
      - QWebEngineView + plotly.js (or Bokeh) for one export action -
        "Export as interactive HTML" - so a chart leaves the app as
        something a reader can hover/zoom/pan in a browser without
        installing anything. Not a render path inside the app: it is a
        second, heavy dependency (Chromium) that only earns its place at
        the export boundary.
      - VisPy/OpenGL is the answer if downsampling (already in Figure
        properties) still is not enough at true multi-million-point series
        - hold until that turns out to be a real ceiling, not a guess.
      - A figure-descriptor -> Vega-Lite spec exporter is a cheap idea
        worth a look later: the descriptors are already a declarative
        JSON-ish shape, which is most of what a Vega-Lite spec is.

      ChartPanel interactivity, roughly in order of how directly they
      build on what is already there (hover readout, pick, context menu):
      - A ruler/measure mode: click two points, show dx/dy/slope as a
        transient annotation - a couple of clicks past the existing hover
        readout.
      - A crosshair synced across every axis of a figure (shared x), and an
        optional "link x zoom/pan across axes" toggle - the standard
        multi-panel-dashboard expectation, and this app's figures are
        already multi-axis.
      - Draggable annotations: let a mouse drag on an annotation's artist
        write its new x/y back to the axis options (the Overlay panel
        already owns that key) instead of only editing it by numbers.
      - Box/lasso multi-select feeding "hide selected" / "new series from
        selection" - the selection half of P2-4, generalized past one
        rectangular region.
      - "Export the current view as data": the rows actually on screen
        after zoom and downsampling, as CSV - a natural sibling of the
        existing copy/save-chart actions.
      - A live/streaming toggle: redraw a chart on a timer, or when its
        source table changes, for a rig or a long-running import someone
        is watching fill in.

      Broader, beyond the chart itself - things a data scientist, an
      engineer or a student doing coursework would reach for:
      - Notebook/script export: a figure's series are already SQL queries
        plus a style dict, which is most of a pandas+matplotlib script or a
        .ipynb cell already written - export it for handoff/reproducibility
        outside this app.
      - Unit-aware axes (pint): an axis label carries a unit, and a
        "convert units" action rescales the display without touching the
        underlying SQL - useful wherever engineering data mixes unit
        systems.
      - Uncertainty propagation: a series operation combining two series
        with error columns (A+-dA op B+-dB) via the standard propagation
        formulas, output as a value + error series pair.
      - A one-click "chart + operation reports -> PDF/HTML" bundle -
        formalizing what results_published/set_notes_html already produce
        per operation into one exportable document.
      - A small scripting console (Python or SQL) against the current
        project's repo, for the point where a power user iterates faster
        typing than clicking through dialogs - the same repo the series
        operations already use, just without a dialog in front of it.

P2-15 series operations: scikit-learn models
      Five candidates, roughly in this order:
      - Transform: PowerTransformer (Yeo-Johnson/Box-Cox), QuantileTransformer,
        StandardScaler, RobustScaler. Small, and a prerequisite for anything
        that assumes normality (the X-chart, curve fits) on skewed data.
      - GP Regression: GaussianProcessRegressor, kernel = RBF / Matern-3/2 /
        Matern-5/2 / RationalQuadratic (+ WhiteKernel noise). Output is the
        mean series *and* a +/-2 sigma credible band as two more series - the
        one smoother here that quantifies its own uncertainty.
      - Robust / ML regression: RANSACRegressor, HuberRegressor,
        IsotonicRegression (guaranteed monotone), RandomForestRegressor,
        GradientBoostingRegressor. Could be new models on the existing Fit
        dialog rather than a new one - it already has the model_combo/
        params/preview shape this needs.
      - Anomaly detection: extend the existing Outliers dialog with
        IsolationForest, LocalOutlierFactor, OneClassSVM, EllipticEnvelope -
        reuses its hide/preview plumbing, catches shape-aware outliers the
        z-score/IQR models miss.
      - Decomposition: PCA / FastICA / NMF across several selected series on
        a shared x grid -> N component series + an explained-variance
        report. The one new shape here: many series in, many out (blind
        source separation, common-mode removal).
      - Manifold learning: t-SNE / Isomap / LocallyLinearEmbedding, same
        many-in shape as Decomposition above but for the nonlinear
        structure PCA misses - exploratory, so frame the result as "a 2D
        layout", not as a measurement, in whatever report it gets.

P2-18 renderer coverage: chart types Matplotlib supports that this app does
      not yet draw. 29 chart types exist today (app/charts/*.py); checked
      against Matplotlib's own Axes/Axes3D API for what nothing here wraps.
      Candidates worth a renderer, roughly in order of how many requests a
      gap like this tends to generate:
      - Heatmap (imshow/pcolormesh over a regular x/y grid, no
        interpolation): distinct from Contour Plot, which always
        interpolates between levels - a correlation matrix or a raw
        measurement grid wants to show the actual cell values, not a
        smoothed field between them.
      - tricontour / tricontourf: the smooth, level-interpolated sibling of
        the existing Triangular Color Mesh (tripcolor draws flat patches,
        no interpolation) - same relationship Heatmap above has to Contour
        Plot, for scattered rather than gridded data.
      - hexbin: 2D density for a scatter with too many points to read
        individually - the 2D counterpart to Histogram, and a common ask
        wherever ECDF/Histogram already are.
      - eventplot: spike/event raster (parallel tick marks per row) - time-
        stamped events (a raw pass/fail log, a channel of digital signal
        edges) that a line or scatter chart draws as noise.
      - 3D Line Plot (Axes3D.plot): a parametric curve or trajectory in
        three dimensions. Scatter Plot (3D) exists but never connects its
        points in order, which is the one thing a trajectory needs.
      - 3D Bar Chart (Axes3D.bar3d): categorical data in three dimensions -
        the 3D counterpart Bar Chart already has in 2D.
      Not candidates: specgram/psd/csd/cohere/*_spectrum/xcorr/acorr are
      already covered as series operations (spectral_dialog.py) that draw
      their output through the existing Scatter Plot/Time Series renderers
      - a transform belongs there, not as a new axis renderer. polar
      projections and voxels are real gaps too but a bigger architectural
      question (a polar axes changes what "x/y role" even means; voxels are
      heavy and rarely load-bearing) rather than a renderer to drop in.

P2-19 pysym: user-authored Python/symbolic series - a suggested design, not
      yet scoped or agreed
      The ask: a series operation where the user writes Python/symbolic
      (sympy-style) code instead of picking one of the built-in transforms,
      previews it against a chosen series, and applies it to both a chart
      series and a real table under a name the user gives it.
      Sketch:
      - Storage: an internal __pysym__ table (name, code, description,
        created/modified timestamps), the same pattern __import_links__ and
        __table_descriptors__ already use - one row per named snippet, so
        it can be reused across series/figures without retyping it.
      - Editing: a series_operations/pysym_dialog.py following the existing
        SeriesOperationDialogBase shape (source series picker, code editor,
        preview plot, Apply) - reuses P2-12's inline-preview plumbing once
        that lands, rather than a second copy of it.
      - Dual output: Apply both draws the result as a new series (the
        existing ResultSeriesSpec/generated_table_name path every operation
        already uses) and materializes it into a table under the name the
        user typed - the second half is new; nothing today lets a series
        operation name and create a persistent table of its own rather than
        an auto-named "_generated" one.
      - Security, the part this cannot skip: a .dhub file is explicitly
        documented elsewhere in this codebase as something that gets
        emailed and committed without a second thought (see why credentials
        never go in one, app/utils/data_sources.py). Embedding arbitrary
        executable Python in that same file is a materially bigger risk
        than the saved SQL queries it already carries - SQL against one's
        own tables is bounded, Python is not. Do not let __pysym__ code run
        on file open, ever, only on an explicit Apply/Run the user clicks
        for that specific snippet - the same trust model a saved query
        already has - and execute it against a restricted globals dict
        (numpy/pandas/math exposed, no import/open/os/subprocess) rather
        than a bare exec(). A one-time warning the first time a project
        with a non-empty __pysym__ table is opened, naming what that means,
        is worth doing even so - this is closer to a spreadsheet macro than
        to a saved filter.
